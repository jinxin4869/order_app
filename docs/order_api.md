# 注文入力の契約

`createOrder`にはオブジェクトを渡します。不正形式は保存前に`invalid-argument`で拒否します。

| フィールド                                        | 形式                                                                                                       |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `restaurantId`, `tableId`, `items[].item_id`      | 英数字・`_`・`-`の1〜128文字                                                                               |
| `requestId`                                       | 必須。一回の注文操作ごとに発行する英数字・`_`・`-`の1〜128文字                                             |
| `tableToken`                                      | 任意。テーブルのQRトークン（英数字・`_`・`-`の16〜128文字）。[テーブルのQRトークン](table_tokens.md)を参照 |
| `visitId`                                         | 任意。端末の来店ID（英数字・`_`・`-`の1〜128文字）。注文の`visit_id`に保存                                 |
| `customerLanguage`                                | `ja` / `en` / `zh`。省略時は`ja`                                                                           |
| `items`                                           | 1〜100行の配列                                                                                             |
| `items[].quantity`                                | 1〜99の整数                                                                                                |
| `items[].price`, `subtotal`, `tax`, `totalAmount` | 円単位の非負整数。各入力の上限は1,000,000,000円                                                            |
| `items[].notes`, `customerNotes`                  | 任意。文字列またはnull、200文字以下                                                                        |

1件の注文の数量の合計は100個まで（`MAX_ORDER_TOTAL_QUANTITY`）です。超える注文は`invalid-argument`（`details.reason = "too_many_items"`、`details.max = 100`）で拒否します。
同じ商品IDと備考（HTMLタグと前後の空白を除いた後）の行が2つ以上ある注文も、合算せずに`invalid-argument`（`details.reason = "duplicate_line"`、`details.itemId`）で拒否します。カートは同じ商品・備考を1行にまとめるため、正しい画面からは送られません。備考が違えば、同じ商品を別の行で注文できます。

備考は`notes`に統一し、旧`special_request`は受け付けません。
保存時にHTMLタグと前後の空白を除去します。画面でも備考をテキストとして表示してください。

送信された商品名は注文履歴の根拠にしません。サーバーが店舗の商品マスターから
`name_ja`・`name_en`・`name_zh`を読み、注文時点のスナップショットとして保存します。
英語・中国語の名前は、メニューの表示と同じ条件（[翻訳の生成・比較](translation_contract.md)）を満たすものだけを保存します。翻訳の来歴（`name_en_translation`など）の原文（`sourceText`）が現在の`name_ja`と一致し、状態が`ready`か`partial`のときです。商品名を変えて翻訳を更新する前の注文や、来歴のない旧データの訳は`null`で保存し、注文履歴は日本語名を表示します。
表示用の`name`は注文言語の名前、欠損時は日本語名になります。

テーブル番号も、送信値ではなくサーバーがテーブルマスターの`table_number`を読み、注文の`table_number`に保存します。
文字列（前後の空白を除いて1〜32文字）または非負の整数を受け付け、文字列として保存します。
マスターに番号がない・形式が不正な場合は`null`です。注文後にマスターの番号を変更しても、過去の注文の番号は変わりません。
スタッフ画面は番号を「テーブル 12」と表示し、番号がない注文（記録を始める前の注文を含む）は
「テーブル番号未記録（ID: table-01）」のように内部IDで識別できるようにします。過去の注文へ現在の番号を後から補完することはしません。

## 価格・受付状態

店舗が受付中で、テーブルが利用可能、かつ店舗配下の商品が公開中・販売中（カテゴリも公開中）の場合だけ受理します。
スタッフによる受付停止（`ordering_paused`）、受付設定の不備（`ordering_unconfigured`）、売り切れ・非公開の商品（`item_unavailable`と`itemId`）はトランザクション内で判定し、`failed-precondition`で拒否します。詳細は[メニュー管理](menu_management.md)を参照してください。
単価は商品マスターと一致する必要があります。価格変更・改変時は`failed-precondition`
（`details.reason = "price_changed"`）で拒否し、メニューを取得し直して商品を選び直します。
価格の違いを黙って反映して注文することはありません。

新規注文の回数はテーブル・店舗ごとに制限します（`rate_limited`）。詳細は[新規注文の連投制限](order_limits.md)を参照してください。

小計・税・合計もサーバーで計算し、送信値が一致しない注文は`invalid-argument`（`details.reason = "total_mismatch"`）で拒否します。

### 金額の計算と表示

商品の価格は税抜で登録し、お客様の画面には税込で表示します。合計は、画面に出ている税込の価格を足した金額です。

| 項目                   | 規則                                                              |
| ---------------------- | ----------------------------------------------------------------- |
| 税率                   | 10%（店内飲食）。軽減税率・複数税率には対応していません           |
| 税込の単価             | 税抜の単価 × 1.1 の円未満を切り捨て（例：95円 → 104円）           |
| 行の金額               | 税込の単価 × 数量（例：104円 × 2 = 208円）                        |
| 合計（`total_amount`） | 行の金額の合算。お客様が支払う金額                                |
| 小計（`subtotal`）     | 税抜の単価 × 数量の合算                                           |
| 税（`tax`）            | 合計 − 小計（上の例では18円）。レシートの消費税額等ではありません |

- 規則は`functions/src/utils/orderTotals.js`の1か所にあり、サーバー（注文の受付・スタッフの訂正）と画面（カート・訂正の目安）が同じ関数を使います。税率・端数処理・合算の順序を変えるときは、このファイルだけを直します。
- サーバーは送信された金額との完全な一致を求めるため、規則を変えた版はFunctionsとHostingを同時にデプロイします。片方だけが新しいと、端数の出る注文が`total_mismatch`で拒否されます。
- 税込で表示し、税込の単価を合算する方針は暫定です。店舗の紙のメニューの表記とレジの計算方法は未確認で、確認した結果に合わせて見直します（[受け入れ確認](acceptance_test_plan.md)の「レジの計算方式との照合」）。
- 表示するのは、メニューの行と商品の詳細（税込の単価）、カートの行（行の金額と、2点以上のときは税込の単価 × 数量）、カートの合計、確定前の確認、注文完了の画面、注文履歴です。表記は日本語「（税込）」、英語「(incl. tax)」、中国語「（含税）」です。スタッフの注文詳細の単価も税込です。メニュー管理の入力と一覧は税抜で、入力欄の下にお客様の画面での表示（税込）を出します。
- 保存済みの注文の金額は書き換えません。以前の規則（小計に対する税額の切り捨て）で受け付けた注文は、その合計のまま表示します。スタッフが訂正したときだけ、注文全体を現在の規則で計算し直すため、減らした商品の金額（税込）に加えて、合計が下がることがあります。下がる幅は、「税（`tax`）とレジの合計」の「端数の差」を訂正前の商品で計算して円未満を切り捨てた額で、訂正前の商品1点あたり0.9円までです（例：以前の規則で受け付けた95円 × 2点は209円。1点に減らすと104円になり、1点分の104円に加えて1円下がります）。訂正前の合計は`original_total_amount`と訂正の記録に残ります。

スタッフが商品を訂正（減数・取消）した注文は、訂正後の数量と金額を持ち、元の数量と合計も残します（[スタッフ認証・店舗権限](staff_access.md)の「商品の訂正」）。訂正のあとに同じ`requestId`で再送しても、返るのは元の受付結果（注文IDと番号）だけで、訂正前の内容に戻ることはありません。

#### 税（`tax`）とレジの合計

税込の単価を商品ごとに切り捨ててから足すため、税抜の合計に税率を掛ける計算とは、合計と税が次の「端数の差」だけずれます。

端数の差 =（数量 × 税抜の単価の1の位）の合算 ÷ 10（円。商品1点あたり0.9円まで）

| 注文（税抜の単価 × 数量） | 小計  | 税（`tax`） | 合計   | 税抜の合計 × 1.1（切り捨て） | 端数の差 |
| ------------------------- | ----- | ----------- | ------ | ---------------------------- | -------- |
| 95円 × 2                  | 190   | 18          | 208    | 209                          | 1.0      |
| 95円 × 3                  | 285   | 27          | 312    | 313                          | 1.5      |
| 19円 × 10                 | 190   | 10          | 200    | 209                          | 9.0      |
| 999円 × 10                | 9,990 | 990         | 10,980 | 10,989                       | 9.0      |
| 500円 × 3、1,200円 × 1    | 2,700 | 270         | 2,970  | 2,970                        | 0        |

- **税（`tax`）**：小計の10%（円未満切り捨て）より、端数の差の円未満を切り捨てた額だけ少なくなります（95円 × 2点では、小計190円の10%は19円、`tax`は18円）。
- **`tax`はレシートに記載する消費税額等ではありません**：消費税法基本通達1-8-15は、適格請求書に記載する消費税額等の端数処理を「一の適格請求書につき、税率の異なるごとにそれぞれ1回」とし、商品ごとに端数処理をして合計した金額を消費税額等とすることはできないとしています（[国税庁 消費税法基本通達 第1章第8節](https://www.nta.go.jp/law/tsutatsu/kihon/shohi/01/08.htm)）。`tax`は商品ごとに端数処理した金額を合算して出した差額で、この方法で計算した額ではありません（19円 × 10点では`tax`は10円ですが、合計200円 × 10/110は18.18…円です）。アプリはレシートを発行せず、`tax`を画面にも表示しません。レジとの突き合わせは合計（`total_amount`）で行います。
- **レジが税抜の合計に税率を掛ける方式の場合**：レジの請求額が、アプリの合計より高くなることがあります。アプリの合計のほうが高くなることはありません。差は、端数の差の円未満をレジの端数処理（切り捨て・四捨五入・切り上げ）で処理した額です。切り捨てのレジでは、多くても「0.9 × 点数」の円未満を切り捨てた額です（税抜の単価の1の位が9の商品10点で9円）。四捨五入・切り上げのレジでは、これより1円多くなることがあります（95円 × 1点は、アプリが104円、レジが105円）。
- **一致する条件**：すべての商品の税抜の単価が10円の倍数なら、端数の差は0で、どの方式・どの端数処理でも合計は一致し、`tax`も小計の10%になります。
- **総額表示との関係**：財務省は、総額表示のもとで税抜価格を基に計算するレジを使う場合について「消費者との間でトラブルが発生する場合があります」とし、税込価格を基に計算するレジへの変更、それが難しい場合は「消費税の計算上、レジでの精算の際に合計額が異なる場合がある」旨の周知を挙げています。総額表示義務はレジシステムの変更を義務付けるものではない、ともしています（[財務省「総額表示に関する主な質問」Q15](https://www.mof.go.jp/tax_policy/summary/consumption/a_001.htm)）。
- ここに書いたのは一次情報の記述と計算の結果で、税務上の助言ではありません。店舗のレジの方式は未確認です。

## 再送と二重注文の防止

クライアントは確定操作の前に`requestId`を作り、通信エラー後の再送にも同じIDを使います。
「同じ内容」は店舗・テーブル・注文備考と、各行の商品ID・数量・単価・備考で判定します。表示言語と翻訳済みの商品名は含めません。
同じ内容の再送では、最初に送った内容（言語を含む）をそのまま送ります。そのため、応答が失われたあとに言語を変えて再送しても、サーバーは同じ注文として扱います。小計・税・合計だけは再送のたびに現在の規則で計算した値を送ります（金額は「同じ内容」の判定に含まれず、サーバーも同じ注文かどうかの照合に使いません）。
数量などを変えた場合は新しいIDです。成功してカートを空にした後の追加注文も新しいIDです。
ただし、結果が不明な送信が残っている間は、新しいIDを作る前にその送信の結果を確認します（「結果が不明なまま内容を変えて確定した場合」）。

サーバーは店舗・テーブル・リクエストID単位で処理済み結果を保存します。同じID・内容の再送は
元の注文IDと番号を返し、異なる内容でのID再利用は`already-exists`で拒否します。
注文・処理済み記録・テーブル更新は一つのFirestoreトランザクションで確定します。
処理済み記録はクライアントから読み書きできません。

### 通信が切れたときの自動の再送

応答を受け取れなかった呼び出しは、アプリが自動で送り直します（`src/utils/errorHandler.js`の`withRetry`）。送り直すのは次の2つの場合だけです。

- 通信が切れて、ブラウザが応答を読めなかった場合。Functions SDKはこれを`functions/internal`（メッセージ`internal [0]`、HTTPステータス0）として報告します。サーバー側の障害でCORSヘッダのない応答が返った場合も、ブラウザからは同じ形に見えるため送り直します。
- `unavailable`（HTTP 503）が返った場合。

サーバーが返した拒否（権限、価格の変更、受付の停止、連投の制限など）と内部エラー（HTTP 500）は送り直しません。SDKの70秒のタイムアウト（`functions/deadline-exceeded`）も送り直しません。すでに70秒待ったお客様を、さらに待たせないためです。

| 呼び出し                                                                                      | 試行回数 | 試行の間の待ち時間 |
| --------------------------------------------------------------------------------------------- | -------- | ------------------ |
| `createOrder`・`getMenuWithTranslation`                                                       | 最大3回  | 1秒、2秒           |
| `validateQRCode`・`getOrderRequest`・`listVisitOrders`・`translateText`・`batchTranslateMenu` | 最大2回  | 1秒                |

注文は毎回同じ`requestId`で送るため、先の送信がサーバーに届いていても重複せず、連投の制限にも数えません。ほかの対象は、読み取りか、同じ結果を書き直す処理です。注文の状態の変更・商品の訂正・来店の終了・メニュー管理の操作は、自動では送り直しません。

オフラインのようにすぐ失敗する場合、エラーを表示するまでに増える待ち時間は、3回の呼び出しで3秒、2回の呼び出しで1秒です。1回の試行は最長70秒なので、どの試行も失敗までに時間がかかった場合の上限は、3回の呼び出しで213秒（70秒×3＋3秒）、2回の呼び出しで141秒（70秒×2＋1秒）です。すべての試行が失敗したときは通信のエラーとして扱い、メニューの取得では「ネットワーク接続を確認してください」と表示します。注文の確定では、下の「送信結果が不明な注文の復旧」の案内を表示します。

## 送信結果が不明な注文の復旧

送信の直前に、端末へ送信内容（`requestId`を含む）・店舗とテーブル・保存時刻を1件だけ保存します（AsyncStorage。Webではlocal storage）。
通信が失敗して結果がわからない場合、画面は「注文の結果を確認できませんでした。…同じ内容なら注文は重複しません」と案内します。サーバーがはっきり拒否した場合（`invalid-argument`・`failed-precondition`・`not-found`・`already-exists`）は、内容の確認を案内します。

ページの再読み込みなどで同じ店舗・テーブルを開き直すと、保存した注文について`getOrderRequest`で受付状況を確認し、メニューとカートの上に案内を出します。

| 確認の結果   | 表示と操作                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 確認中       | 「前回の注文の受付状況を確認しています…」                                                                                                                 |
| 受付済み     | 注文番号を表示し、「注文内容を見る」で注文完了画面へ。保存した記録は消します                                                                              |
| 未受付       | 「カートに戻す」で商品を戻します。内容を変えずに確定すると同じ`requestId`で送るため、元の送信があとから届いても重複しません。「破棄する」で記録を消します |
| 確認できない | 「もう一度確認する」だけを出します。未受付と決めつけません                                                                                                |

### 結果が不明なまま内容を変えて確定した場合

結果が不明な送信が残っている状態で、カートの内容を変えて「注文を確定する」を押すと、新しい`requestId`を作る前に、先の`requestId`を`getOrderRequest`で確認します。確認が終わるまで、新しい注文は送信しません。再読み込みのあとに案内が出ている状態で、別の内容を確定した場合も同じです。

| 先の送信     | 動作                                                                                                                                                                                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 受付済み     | 新しい注文は送信しません。「前回の注文は受付済みです」と知らせ、上の表の「受付済み」の案内を出します。受付済みの商品（商品IDと備考が同じ行）は、その数量だけカートから除きます。残るのはあとから足した分だけで、次の確定で追加の注文（新しいID）になります |
| 未受付       | 変更後の内容を新しいIDで送信します。保存した記録は新しい送信に置き換えます                                                                                                                                                                                 |
| 確認できない | 新しい注文は送信しません。「前回の注文を確認できません」と知らせ、上の表の「確認できない」の案内を出します。カートはそのまま残ります。もう一度確定を押すか「もう一度確認する」を押すと、確認し直します。内容を元に戻して確定した場合は、同じIDで再送します |

受付済みと分かったときに受付済みの商品をカートから除く動作は、再読み込み後の確認と「もう一度確認する」でも同じです。先の注文の数量を減らしたい場合など、受付済みの注文そのものの変更は、スタッフが訂正します。

未受付の確認は、確認した時点の結果です。確認のあとに先の送信がサーバーへ届いた場合は、別の注文として受け付けられます。

`getOrderRequest`には`restaurantId`・`tableId`・`requestId`（英数字・`_`・`-`の1〜128文字）を渡し、`{ accepted: false }`または`{ accepted: true, orderId, orderNumber }`を受け取ります。
`requestId`は送信した端末だけが持つ乱数（UUID）で、店舗・テーブルとの組み合わせが一致しないと結果を返しません。注文の内容や金額は返しません。

保存した記録は、注文の成功、価格変更による選び直し、「破棄する」、別の店舗・テーブルを開いたとき、保存から3時間を過ぎたときに消します。QRの入口や`/order`の検証画面を経由する再読み込みでは消しません。
ページの再読み込みで復元するのは、この送信済みの注文だけです。送信していないカートの商品は、これまでどおり復元しません。

## 来店単位の注文履歴

お客様は「注文履歴」（メニュー画面のヘッダー、注文完了画面）で、来店中にこの端末から送った注文と進行状況を確認できます。ログインは不要です。

- **来店ID**：端末がテーブルごとに乱数（UUID）の`visitId`を作って保存し（AsyncStorage）、注文ごとに送ります。同じテーブルなら再読み込みや追加注文でも同じIDを使います。別の店舗・テーブルを開くと、新しい来店IDになります。
- **取得**：`listVisitOrders({ restaurantId, tableId, visitId })`は、その来店IDで同じ店舗・テーブルに送った注文を新しい順に最大100件返します。返すのは注文番号・状態・合計・時刻・商品名（日英中）・数量・単価・商品備考だけです。注文全体の備考、スタッフの情報、内部の記録は返しません。来店IDを知らなければ、店舗・テーブル・注文IDから履歴を取得できません。
- **来店の終了**：スタッフが「このテーブルの来店を終了する」を押すと、テーブルを空席に戻し、終了時刻（`visit_closed_at`）を記録します。それ以前の注文は来店IDで取得できなくなり、`closed: true`を返します。端末はそれを受けて新しい来店IDを作るため、次のお客様や同じ端末の次の来店と履歴が混ざりません。
- **期限**：終了の操作がなくても、作成から12時間を過ぎた注文は返しません（端末の来店IDも12時間で作り直します）。
- **同席者との共有**：初期版では共有しません。同じテーブルの別の端末から送った注文は表示しません。共有が必要になった場合は、来店IDを同席者の端末へ渡す仕組みを別途設計します。
- **確定した注文だけを表示**：履歴に出るのはサーバーが受け付けた注文だけです。送信中や結果が不明な注文は、上の「送信結果が不明な注文の復旧」の案内で扱い、受付済みとは表示しません。取得に失敗したときやオフラインのときは「表示中の内容は最新ではない可能性があります」と表示します。表示中は15秒ごと、画面に戻ったとき、「更新」で取り直します。

## 営業日と注文番号

営業日は**日本時間（Asia/Tokyo）の0時**に切り替えます。注文番号は`YYYYMMDD-001`の形式です。
店舗・営業日ごとの`restaurants/{restaurantId}/order_counters/{YYYYMMDD}`に
`last_sequence`を保存し、注文と同じトランザクションで増やします。
注文には採番に使った`business_day`も保存します。日付をまたいだ再送は元の番号を返します。

新規運用は最初の注文から自動でカウンターを作ります。既存方式から移行する場合は、
新しい営業日の初回注文前に切り替えるか、受付を止めて管理者がその日の発行済み最大番号を
`last_sequence`に設定してから再開してください。番号の重複を防ぐため、既存注文がある日に
カウンターだけ欠けている場合は`counter_initialization_required`で受付を止めます。
この確認にはインデックス付きの最大1件の検索を使い、全注文の件数から採番しません。
`firestore.indexes.json`のインデックスも先に反映してください。

## カートのセッション

カートは店舗IDとテーブルIDの組に紐付きます。同じテーブルの言語選択・メニュー・商品詳細・カートの移動では保持します。
店舗またはテーブルを変更した場合、またはQRの入口へ戻った場合は、未注文のカートと送信IDを破棄します。
追加注文は、注文成功で空になった同じテーブルのカートから始めます。

Webでは注文中も`/order?restaurant=...&table=...`を保ちます。再読み込み時はサーバー検証からやり直します。
カートはメモリー上の状態であり、ページを再読み込みすると未確定の商品は復元しません（送信済みで結果が不明な注文は、上の「送信結果が不明な注文の復旧」で扱います）。

数量の最小値1・最大値99は`functions/src/utils/orderLimits.js`を画面・フック・APIで共有します。
上限は同じ商品IDと備考のカート行ごとに適用します。カート内の既存数量も含めて99個までとし、
上限に達した行は増加ボタンを無効化します。詳細画面では追加可能な残数を超えて選択できません。
フックへの上限超過の追加・更新は99に制限し、不正な小数・非数値は受け付けません。
APIへの範囲外数量は`invalid-argument`で拒否します。

1件の注文の合計数量の上限（100個）も同じファイルで共有します。カートは合計が100個に達すると「1回の注文は合計100個までです（カート内N個）」と表示し、すべての行の増加ボタンを無効にします。メニューや商品の詳細からの追加で100個を超えた場合は、数量を減らすよう表示し、注文を確定できません。

注文送信後に店舗・テーブルを切り替えた場合、旧セッションの成功・失敗応答では新しいカートを消去したり画面遷移したりしません。旧セッションで開いた価格変更の確認も無効になります。同じテーブルへ戻っても旧送信IDは復活しません。これは送信済み注文の取り消しではなく、結果の画面反映を現在のセッションに限定する動作です。
