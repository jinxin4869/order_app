# 注文入力の契約

`createOrder`にはオブジェクトを渡します。不正形式は保存前に`invalid-argument`で拒否します。

| フィールド                                        | 形式                                                                       |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| `restaurantId`, `tableId`, `items[].item_id`      | 英数字・`_`・`-`の1〜128文字                                               |
| `requestId`                                       | 必須。一回の注文操作ごとに発行する英数字・`_`・`-`の1〜128文字             |
| `visitId`                                         | 任意。端末の来店ID（英数字・`_`・`-`の1〜128文字）。注文の`visit_id`に保存 |
| `customerLanguage`                                | `ja` / `en` / `zh`。省略時は`ja`                                           |
| `items`                                           | 1〜100行の配列                                                             |
| `items[].quantity`                                | 1〜99の整数                                                                |
| `items[].price`, `subtotal`, `tax`, `totalAmount` | 円単位の非負整数。各入力の上限は1,000,000,000円                            |
| `items[].notes`, `customerNotes`                  | 任意。文字列またはnull、200文字以下                                        |

備考は`notes`に統一し、旧`special_request`は受け付けません。
保存時にHTMLタグと前後の空白を除去します。画面でも備考をテキストとして表示してください。

送信された商品名は注文履歴の根拠にしません。サーバーが店舗の商品マスターから
`name_ja`・`name_en`・`name_zh`を読み、注文時点のスナップショットとして保存します。
表示用の`name`は注文言語の名前、欠損時は日本語名になります。

テーブル番号も、送信値ではなくサーバーがテーブルマスターの`table_number`を読み、注文の`table_number`に保存します。
文字列（前後の空白を除いて1〜32文字）または非負の整数を受け付け、文字列として保存します。
マスターに番号がない・形式が不正な場合は`null`です。注文後にマスターの番号を変更しても、過去の注文の番号は変わりません。
スタッフ画面は番号を「テーブル 12」と表示し、番号がない注文（記録を始める前の注文を含む）は
「テーブル番号未記録（ID: table-01）」のように内部IDで識別できるようにします。過去の注文へ現在の番号を後から補完することはしません。

## 価格・受付状態

店舗が受付中で、テーブルが利用可能、かつ店舗配下の商品が公開中・販売中（カテゴリも公開中）の場合だけ受理します。
スタッフによる受付停止（`ordering_paused`）、受付設定の不備（`ordering_unconfigured`）、売り切れ・非公開の商品（`item_unavailable`と`itemId`）はトランザクション内で判定し、`failed-precondition`で拒否します。詳細は[メニュー管理](menu_management.md)を参照してください。
単価は商品マスターと一致する必要があります。価格変更・改変時は`failed-precondition`
（`details.reason = "price_changed"`）で拒否し、メニューを取得し直して商品を選び直します。
価格の違いを黙って反映して注文することはありません。

新規注文の回数はテーブル・店舗ごとに制限します（`rate_limited`）。詳細は[新規注文の連投制限](order_limits.md)を参照してください。

小計・税・合計もサーバーで計算し、送信値が一致しない注文は`invalid-argument`で拒否します。
現行仕様は税抜単価、消費税10%、注文小計に対する税額の円未満切り捨てです。

## 再送と二重注文の防止

クライアントは確定操作の前に`requestId`を作り、通信エラー後の再送にも同じIDを使います。
「同じ内容」は店舗・テーブル・注文備考と、各行の商品ID・数量・単価・備考で判定します。表示言語と翻訳済みの商品名は含めません。
同じ内容の再送では、最初に送った内容（言語を含む）をそのまま送ります。そのため、応答が失われたあとに言語を変えて再送しても、サーバーは同じ注文として扱います。
数量などを変えた場合は新しいIDです。成功してカートを空にした後の追加注文も新しいIDです。

サーバーは店舗・テーブル・リクエストID単位で処理済み結果を保存します。同じID・内容の再送は
元の注文IDと番号を返し、異なる内容でのID再利用は`already-exists`で拒否します。
注文・処理済み記録・テーブル更新は一つのFirestoreトランザクションで確定します。
処理済み記録はクライアントから読み書きできません。

## 送信結果が不明な注文の復旧

送信の直前に、端末へ送信内容（`requestId`を含む）・店舗とテーブル・保存時刻を1件だけ保存します（AsyncStorage。Webではlocal storage）。
通信が失敗して結果がわからない場合、画面は「注文の結果を確認できませんでした。…同じ内容なら注文は重複しません」と案内します。サーバーがはっきり拒否した場合（`invalid-argument`・`failed-precondition`・`not-found`・`already-exists`）は、内容の確認を案内します。

ページの再読み込みなどで同じ店舗・テーブルを開き直すと、保存した注文について`getOrderRequest`で受付状況を確認し、メニューとカートの上に案内を出します。

| 確認の結果   | 表示と操作                                                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 確認中       | 「前回の注文の受付状況を確認しています…」                                                                                                                 |
| 受付済み     | 注文番号を表示し、「注文内容を見る」で注文完了画面へ。保存した記録は消します                                                                              |
| 未受付       | 「カートに戻す」で商品を戻します。内容を変えずに確定すると同じ`requestId`で送るため、元の送信があとから届いても重複しません。「破棄する」で記録を消します |
| 確認できない | 「もう一度確認する」だけを出します。未受付と決めつけません                                                                                                |

`getOrderRequest`には`restaurantId`・`tableId`・`requestId`（英数字・`_`・`-`の1〜128文字）を渡し、`{ accepted: false }`または`{ accepted: true, orderId, orderNumber }`を受け取ります。
`requestId`は送信した端末だけが持つ乱数（UUID）で、店舗・テーブルとの組み合わせが一致しないと結果を返しません。注文の内容や金額は返しません。

保存した記録は、注文の成功、価格変更による選び直し、「破棄する」、別の店舗・テーブルを開いたとき、保存から3時間を過ぎたときに消します。QRの入口や`/order`の検証画面を経由する再読み込みでは消しません。
ページの再読み込みで復元するのは、この送信済みの注文だけです。送信していないカートの商品は、これまでどおり復元しません。

## 来店単位の注文履歴

お客様は「注文履歴」（メニュー画面のヘッダー、注文完了画面）で、来店中にこの端末から送った注文と進行状況を確認できます。ログインは不要です。

- **来店ID**：端末がテーブルごとに乱数（UUID）の`visitId`を作って保存し（AsyncStorage）、注文ごとに送ります。同じテーブルなら再読み込みや追加注文でも同じIDを使います。別の店舗・テーブルを開くと、新しい来店IDになります。
- **取得**：`listVisitOrders({ restaurantId, tableId, visitId })`は、その来店IDで同じ店舗・テーブルに送った注文を新しい順に最大100件返します。返すのは注文番号・状態・合計・時刻・商品名（日英中）・数量・単価・商品備考だけです。注文全体の備考、スタッフの情報、内部の記録は返しません。来店IDを知らなければ、店舗・テーブル・注文IDから履歴を取得できません。
- **来店の終了**：スタッフが「このテーブルの来店を終了する」を押すと、テーブルを空席に戻し、終了時刻（`visit_closed_at`）を記録します。それ以前の注文は来店IDで取得できなくなり、`closed: true`を返します。端末はそれを受けて新しい来店IDを作るため、次のお客様や同じ端末の次の来店と履歴が混ざりません。
- **期限**：終了の操作がなくても、作成から12時間を過ぎた注文は返しません（端末の来店IDも12時間で作り直します）。
- **同席者との共有**：初期版では共有しません。同じテーブルの別の端末から送った注文は表示しません。共有が必要になった場合は、来店IDを同席者の端末へ渡す仕組みを別途設計します。
- **確定した注文だけを表示**：履歴に出るのはサーバーが受け付けた注文だけです。送信中や結果が不明な注文は、上の「送信結果が不明な注文の復旧」の案内で扱い、受付済みとは表示しません。取得に失敗したときやオフラインのときは「表示中の内容は最新ではない可能性があります」と表示します。表示中は15秒ごと、画面に戻ったとき、「更新」で取り直します。

## 営業日と注文番号

営業日は**日本時間（Asia/Tokyo）の0時**に切り替えます。注文番号は`YYYYMMDD-001`の形式です。
店舗・営業日ごとの`restaurants/{restaurantId}/order_counters/{YYYYMMDD}`に
`last_sequence`を保存し、注文と同じトランザクションで増やします。
注文には採番に使った`business_day`も保存します。日付をまたいだ再送は元の番号を返します。

新規運用は最初の注文から自動でカウンターを作ります。既存方式から移行する場合は、
新しい営業日の初回注文前に切り替えるか、受付を止めて管理者がその日の発行済み最大番号を
`last_sequence`に設定してから再開してください。番号の重複を防ぐため、既存注文がある日に
カウンターだけ欠けている場合は`counter_initialization_required`で受付を止めます。
この確認にはインデックス付きの最大1件の検索を使い、全注文の件数から採番しません。
`firestore.indexes.json`のインデックスも先に反映してください。

## カートのセッション

カートは店舗IDとテーブルIDの組に紐付きます。同じテーブルの言語選択・メニュー・商品詳細・カートの移動では保持します。
店舗またはテーブルを変更した場合、またはQRの入口へ戻った場合は、未注文のカートと送信IDを破棄します。
追加注文は、注文成功で空になった同じテーブルのカートから始めます。

Webでは注文中も`/order?restaurant=...&table=...`を保ちます。再読み込み時はサーバー検証からやり直します。
カートはメモリー上の状態であり、ページを再読み込みすると未確定の商品は復元しません（送信済みで結果が不明な注文は、上の「送信結果が不明な注文の復旧」で扱います）。

数量の最小値1・最大値99は`functions/src/utils/orderLimits.js`を画面・フック・APIで共有します。
上限は同じ商品IDと備考のカート行ごとに適用します。カート内の既存数量も含めて99個までとし、
上限に達した行は増加ボタンを無効化します。詳細画面では追加可能な残数を超えて選択できません。
フックへの上限超過の追加・更新は99に制限し、不正な小数・非数値は受け付けません。
APIへの範囲外数量は`invalid-argument`で拒否します。

注文送信後に店舗・テーブルを切り替えた場合、旧セッションの成功・失敗応答では新しいカートを消去したり画面遷移したりしません。旧セッションで開いた価格変更の確認も無効になります。同じテーブルへ戻っても旧送信IDは復活しません。これは送信済み注文の取り消しではなく、結果の画面反映を現在のセッションに限定する動作です。
