# メニュー・注文データのバックアップと復元

データの誤った変更・削除や環境の障害のあとに、必要なデータと設定を復元できるようにするための手順です。本番のバックアップの設定と復元の実施には、Firebase / Google Cloudの権限が必要です。

## 対象と対象外

| データ                                  | 場所                                                              | 扱い           | 理由                                                                                                |
| --------------------------------------- | ----------------------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------- |
| 店舗・テーブル                          | `restaurants/{r}`、`.../tables`                                   | 対象           | 営業に必須                                                                                          |
| カテゴリ・商品・下書き・操作記録        | `.../menu_categories`、`menu_items`、`menu_drafts`、`menu_events` | 対象           | メニューの表示・販売状態・編集の経緯                                                                |
| 注文番号のカウンター                    | `.../order_counters/{YYYYMMDD}`                                   | 対象（必須）   | 失うと番号が重複する                                                                                |
| テーブルのQRトークンのハッシュ          | `.../table_secrets`                                               | 対象（必須）   | 失うと、強制が有効な場合に印刷済みのQRが使えなくなる                                                |
| 注文・状態の履歴・訂正                  | `orders`、`orders/{id}/status_history`、`.../corrections`         | 対象           | 受付・対応・訂正の記録                                                                              |
| 処理済みの注文リクエスト                | `order_requests`                                                  | 対象（必須）   | 失うと、復元前に受け付けた注文の再送が二重の注文になる                                              |
| 辞書                                    | `dictionary`                                                      | 対象           | 翻訳の品質                                                                                          |
| 翻訳のキャッシュ                        | `translation_cache`                                               | 任意           | 作り直せるが、DeepLの利用枠を使う                                                                   |
| 連投制限のカウンター                    | `.../rate_limits`                                                 | 対象外         | 短い時間枠の一時的な値。復元しても害はない                                                          |
| スタッフのアカウントとClaims            | Firebase Authentication                                           | 別に扱う       | Firestoreのバックアップに含まれない。`firebase auth:export`で書き出すか、復元後に管理者が発行し直す |
| ルール・インデックス・Functionsのコード | Gitの`firestore.rules`、`firestore.indexes.json`、`functions/`    | Gitで管理      | 復元先へデプロイし直す                                                                              |
| Functionsの設定・秘密値                 | `functions/.env`、Secret Managerの`DEEPL_API_KEY`                 | 別に安全に保管 | リポジトリに置かない。復元先で設定し直す                                                            |
| WebのビルドとHosting                    | Gitのソース                                                       | Gitで管理      | `npx expo export`でビルドし直してデプロイ                                                           |

秘密鍵・環境ファイル・パスワード・Authの書き出し（パスワードのハッシュを含む）は、リポジトリや手順書に含めず、権限を絞った場所に保管してください。

## 頻度・保持・目標（運用開始時に確定する案）

| 項目                      | 案                                                                     |
| ------------------------- | ---------------------------------------------------------------------- |
| 定期バックアップ          | Firestoreのスケジュールバックアップを毎日（営業終了後）。保持14日      |
| 誤操作への備え            | Point-in-time recovery（7日間）                                        |
| 許容するデータ損失（RPO） | 定期バックアップだけなら最大24時間。PITRを使えば数分                   |
| 復旧の目標（RTO）         | 2時間以内（その間は[注文障害の手順](incident_runbook.md)の紙での受付） |
| 担当                      | システム担当（バックアップの成否の確認と復元の実施）                   |
| 保存先と閲覧の権限        | 同じGoogle Cloudプロジェクト。バックアップの管理者のロールを持つ人だけ |

### 成否の確認

- バックアップの一覧（Firebaseコンソール、または`gcloud firestore backups list`）で、毎日のバックアップができていることを確認します。失敗の通知はCloud Monitoringで設定します。
- 失敗したときは、その日のうちに手動のバックアップ（または書き出し）を取り、原因を記録します。

## 復元の手順

1. **影響を止める**：[メニュー管理](menu_management.md)で注文受付を停止し、紙での受付に切り替えます。
2. **対象を確かめる**：復元するバックアップの時刻、復元先のプロジェクトとデータベースIDを、2人で確認して記録します。**本番の既定のデータベースへ直接上書きしません。**
3. **別のデータベースに復元する**：Firestoreの復元は新しいデータベースを作ります。まずそこへ復元します。
4. **復元先を確かめる**：下の「復元後に確かめること」を、復元したデータベースで確認します。
5. **本番に戻す**：必要なコレクションだけを、確認したうえで本番へ移します（書き出しと読み込み）。ルール・インデックス・Functions・Hostingを必要に応じてデプロイし直し、Authのアカウントを読み込むか、発行し直します。
6. **再開する**：「照合と再開」を行ってから、注文受付を再開します。

### 復元後に確かめること

| 確認     | 内容                                                                       |
| -------- | -------------------------------------------------------------------------- |
| メニュー | お客様のメニュー・売り切れの表示が正しい                                   |
| スタッフ | ログインでき、所属店舗の注文が一覧に出る                                   |
| 採番     | 新しい注文の番号が続きから振られ、受け付け済みの番号を再利用しない         |
| 再送     | 復元前に受け付けた注文の同じ`requestId`の再送が、元の注文を返す            |
| 来店     | 終了した来店は終了したまま。続いている来店は自分の注文だけを表示する       |
| 記録     | 状態の履歴・訂正・メニューの操作記録が残っている                           |
| QR       | 強制が有効なら、印刷済みのQRのトークンが通り、トークンのないQRは拒否される |
| 公開範囲 | ルールにより、クライアントから注文・記録・下書き・トークンを読めない       |

## 照合と再開

- **バックアップの時点より後の注文は失われます。** スタッフの記憶、紙の注文票、お客様の画面（注文完了・注文履歴）、Functionsのログ（店舗IDとエラーの種類）で、その間に受け付けた注文を確認し、紙の注文として対応します。
- **番号の再利用を防ぐ**：失われた注文の番号は、お客様の手元に残っている可能性があります。受付を再開する前に、その日の`order_counters/{YYYYMMDD}`の`last_sequence`を、知られている最大の番号以上に、管理者が設定してください。
- 失われた注文の`requestId`は`order_requests`にないため、お客様が同じ注文を再送すると、新しい注文として受け付けます（受け付けたことが記録上なくなっているため）。二重の調理にならないよう、紙の注文と照合してから調理します。
- 復元の時点より後にスタッフが来店を終了していたテーブルは、もう一度「来店を終了」します。
- 再開の判定は[注文障害の手順](incident_runbook.md)の「再開の判定」と同じです。

## 復元の訓練

- **合成データ（自動）**：`npm run test:backup`は、エミュレーターで本物の処理を使って合成データ（注文・状態の変更・訂正・来店の終了・QRトークン）を作り、書き出したものを新しいエミュレーターに読み込んで、「復元後に確かめること」のメニュー・スタッフ・採番・再送・来店・記録・QRを確かめます。CIでも実行します。本番のデータや秘密値は使いません。
- **本番の訓練（権限が必要）**：運用開始前と、その後は半年に1回、最新のバックアップを別のデータベースへ復元し、上の確認を行って、日付・対象・結果・かかった時間を記録します。
