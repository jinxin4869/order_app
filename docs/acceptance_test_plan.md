# 実店舗導入前の受け入れ確認

CIや合成のブラウザテストに加えて、店舗で想定する端末・通信・人の動きで使えることを確かめ、導入するかを判断するための計画です。この文書は計画と記録の形式で、**実施した結果ではありません**。会計・決済・POS連携は対象外です。

## 前提

- **環境**：本番とは別のFirebaseプロジェクト（テスト用）を使います。メニュー・テーブルは合成データ、スタッフはテスト用のアカウントです。運用環境の機密情報・本番のデータは使いません。
- **翻訳**：テスト用のメニューの翻訳は事前に作っておき、確認中は「翻訳を更新」を押しません（実課金のAPIを使わない）。
- **準備（Firebaseの権限が必要）**：テスト用プロジェクトで、Authentication（メール／パスワード）を有効にし、スタッフのアカウントとClaims（1人は`canEditMenu`も）を発行します。ルール・インデックス・Functions・Hostingをデプロイし、テーブルのQRトークンを発行して、テスト用のQRを印刷します（[テーブルのQRトークン](table_tokens.md)）。強制のスイッチ（QRトークン・連投制限・App Check）は、本番で予定している設定にそろえます。
- **版**：確認するコミットを決め、その版を最後まで使います。途中で直した場合は、影響するシナリオを確認し直します。

## 想定と合否の基準（店舗に合わせて確定する）

| 項目             | 案                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------- |
| 客席・同時の利用 | 20席、同時に10グループ。ピーク時は1分に5件の注文                                                            |
| お客様の端末     | iPhone（Safari、最新とその1つ前のiOS）、Android（Chrome、最新とその1つ前のAndroid）。標準のカメラでQRを読む |
| スタッフの端末   | タブレット（iPadのSafari、AndroidのChrome）、PC（Chrome、Edge）、スマホ（スタッフ自身の端末）               |
| 通信             | 店舗のWi-Fi、モバイル回線（4G/5G）、電波の弱い席、通信の切断と復帰                                          |
| 担当             | 店長（判定）、スタッフ2名（操作）、システム担当（準備・記録）                                               |
| 合格             | すべてのシナリオが期待どおりで、重大度Aの課題が0件。重大度Bの課題は、回避策と修正の期限が決まっている       |

## レジの計算方式との照合

R1の内容です。アプリはレジと連携しないので、お客様が画面で見た合計と、レジで請求される金額が同じになるかを、人が見比べて確かめます。アプリの金額の規則と、レジの方式によるずれの向き・上限は、[注文API契約](order_api.md)の「金額の計算と表示」を参照してください。店舗の紙のメニューの表記とレジの計算方式は、まだ確認できていません。

### 店舗に確認すること

| 項目               | 確認すること                                                 |
| ------------------ | ------------------------------------------------------------ |
| 紙のメニューの価格 | 税込表記か、税抜表記か                                       |
| レジの合計の計算   | 商品ごとの税込の価格を足すのか、税抜の合計に税率を掛けるのか |
| レジの端数処理     | 切り捨て・四捨五入・切り上げのどれか                         |

紙のメニューが税込表記の場合は、メニュー管理の入力欄の下に出る税込の価格が、紙のメニューと同じになることも商品ごとに確かめます。アプリは税抜の価格 × 1.1 の円未満を切り捨てるので、税込1,000円のように、どの税抜の価格を登録しても表示できない価格があります（909円は999円、910円は1,001円）。

### 手順

1. レジに登録されている商品のうち、税抜の単価の1の位が0でないものを2種類以上選び、同じ価格でテスト用のメニューに登録します。
2. その商品をそれぞれ複数点入れた注文をアプリで作り、画面の合計（税込）を記録します。
3. 同じ内容をレジで打ち、請求額を記録します。売上に残らないよう、レジの練習モードを使うか、打ったあとに取り消します。
4. 2つの金額が一致するかを見ます。内容を変えて3件以上で確かめます。

例：税抜455円 × 3点と税抜728円 × 2点の注文では、アプリの合計は3,100円（500円 × 3 + 800円 × 2）です。税抜の合計2,821円に税率を掛けるレジでは、切り捨て・四捨五入で3,103円、切り上げで3,104円になります。

1の位が0でない商品がレジにない場合（すべての税抜の単価が10円の倍数）は、端数が出ず、どの方式でも一致します。その場合も、店舗に確認した内容を記録します。

### 合わなかったときの扱い

一致しなければR1を不合格とし、重大度Aの課題として記録します（「課題の重大度と再確認」）。次のいずれかで対応し、対応した版でR1と、金額を確認するC3・S4を確認し直すまで、合格にしません。

| 対応                                 | 内容                                                                                                                                                                              |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| アプリの計算の規則をレジに合わせる   | `functions/src/utils/orderTotals.js`を直します（規則はこの1か所）。サーバーは送信された金額との完全な一致を求めるので、規則を変えた版はFunctionsとHostingを同じ版でデプロイします |
| レジを、税込の価格を足す方式に変える | 店舗がレジの設定を変えます。アプリは変えません                                                                                                                                    |
| レジを変えられず、アプリの規則も残す | 精算の際に合計が異なる場合がある旨を、お客様の画面に表示します。この表示はまだ実装していません                                                                                    |

3つ目の対応を採る場合は、R1の期待する結果を「差が[注文API契約](order_api.md)に書いた向きと上限に収まり、その旨がお客様の画面に出ている」に読み替えます。

## 記録

シナリオごとに、次の項目を記録します。

| 日付 | 版（コミット） | 端末・OS・ブラウザ | 通信 | シナリオID | 結果（合格／不合格） | 課題ID | 担当 |
| ---- | -------------- | ------------------ | ---- | ---------- | -------------------- | ------ | ---- |

### 課題の重大度と再確認

| 重大度 | 例                                                                                                                         | 扱い                                               |
| ------ | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| A      | 注文の欠落・重複、テーブルの取り違え、ほかのお客様の注文の表示、受付済みと誤認させる表示、画面の合計とレジの請求額の不一致 | 修正して該当のシナリオを確認し直すまで合格にしない |
| B      | 操作はできるが誤解を招く、手順が分かりにくい                                                                               | 回避策と修正の期限を決める                         |
| C      | 表示の崩れ・文言                                                                                                           | 期限を決めて修正する                               |

課題を直したら、修正した版で該当のシナリオと、影響しうるシナリオを確認し直して記録します。

## スタッフへの引き継ぎ

| 場面   | 確認すること                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------ |
| 開店時 | ログイン、「メニュー管理」で受付中であることと前日の売り切れの解除、「通知音をオンにする」       |
| 営業中 | 新着の確認、待ち時間の長い注文、状態の更新、訂正（理由を入れる）、お客様が帰ったら「来店を終了」 |
| 閉店時 | 「集計」で当日の数値を確認、ログアウト（共用の端末）                                             |
| 障害時 | [注文障害の手順](incident_runbook.md)のスタッフ向けの手順                                        |

スタッフが手順書を見ながら、通常の操作と障害時の切り替えをできることを、S1〜S9で確かめます。
