# 実店舗導入前の受け入れ確認

CIや合成のブラウザテストに加えて、店舗で想定する端末・通信・人の動きで使えることを確かめ、導入するかを判断するための計画です。この文書は計画と記録の形式で、**実施した結果ではありません**。会計・決済・POS連携は対象外です。

## 前提

- **環境**：本番とは別のFirebaseプロジェクト（テスト用）を使います。メニュー・テーブルは合成データ、スタッフはテスト用のアカウントです。運用環境の機密情報・本番のデータは使いません。
- **翻訳**：テスト用のメニューの翻訳は事前に作っておき、確認中は「翻訳を更新」を押しません（実課金のAPIを使わない）。
- **準備（Firebaseの権限が必要）**：テスト用プロジェクトで、Authentication（メール／パスワード）を有効にし、スタッフのアカウントとClaims（1人は`canEditMenu`も）を発行します。ルール・インデックス・Functions・Hostingをデプロイし、テーブルのQRトークンを発行して、テスト用のQRを印刷します（[テーブルのQRトークン](table_tokens.md)）。強制のスイッチ（QRトークン・連投制限・App Check）は、本番で予定している設定にそろえます。
- **版**：確認するコミットを決め、その版を最後まで使います。途中で直した場合は、影響するシナリオを確認し直します。

## 想定と合否の基準（店舗に合わせて確定する）

| 項目             | 案                                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------- |
| 客席・同時の利用 | 20席、同時に10グループ。ピーク時は1分に5件の注文                                                            |
| お客様の端末     | iPhone（Safari、最新とその1つ前のiOS）、Android（Chrome、最新とその1つ前のAndroid）。標準のカメラでQRを読む |
| スタッフの端末   | タブレット（iPadのSafari、AndroidのChrome）、PC（Chrome、Edge）、スマホ（スタッフ自身の端末）               |
| 通信             | 店舗のWi-Fi、モバイル回線（4G/5G）、電波の弱い席、通信の切断と復帰                                          |
| 担当             | 店長（判定）、スタッフ2名（操作）、システム担当（準備・記録）                                               |
| 合格             | すべてのシナリオが期待どおりで、重大度Aの課題が0件。重大度Bの課題は、回避策と修正の期限が決まっている       |

## シナリオ

| ID  | シナリオ                                                             | 期待する結果                                                                            |
| --- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| C1  | 標準のカメラでQRを読む → ブラウザで開く                              | 店舗とテーブルが確認され、言語の選択に進む。URLにトークンが残る                         |
| C2  | 日本語・英語・中国語を切り替える、翻訳の比較（辞書あり／なし）       | 表示が切り替わる。未生成・未確認の翻訳はその旨が表示される                              |
| C3  | 商品を選んで注文する                                                 | 注文番号が表示され、スタッフの一覧に届く                                                |
| C4  | 同じテーブルの複数人が、それぞれの端末から注文する                   | 各注文が別々に届き、各端末の注文履歴には自分の注文だけが出る                            |
| C5  | 別のテーブルから同時に注文する                                       | テーブル番号が正しく、取り違えがない                                                    |
| C6  | 追加注文をする                                                       | 新しい注文番号で届き、注文履歴に並ぶ                                                    |
| C7  | スタッフが来店を終了し、次のお客様が同じテーブルで注文する           | 前のお客様の注文は次のお客様の注文履歴に出ない                                          |
| C8  | 端末のスリープ、再読み込み、ブラウザの戻る                           | 状態を誤認させず、カートと注文の結果が正しく表示される                                  |
| C9  | 送信中に機内モードにする（応答の欠落）→ 戻して再送、または再読み込み | 注文が重複しない。受付済みなら「前回の注文は受け付けられています」                      |
| C10 | 注文の直前に、スタッフが売り切れ・受付停止にする                     | 注文全体が止まり、売り切れの行・停止の案内が出る。カートは残る                          |
| C11 | 短時間に多くの注文を送る（強制を有効にした場合）                     | 制限の案内が出て、スタッフ画面に記録が出る。通常の追加注文は止まらない                  |
| S1  | スタッフがログインし、新着の通知（音・タブの表示）を確認する         | 新着が知らされる。音が出ない端末でも画面で分かる                                        |
| S2  | 受付 → 調理 → 提供待ち → 提供済み → 対応完了                         | 状態が変わり、操作履歴に残る                                                            |
| S3  | 2台のスタッフ端末で同じ注文を同時に操作する                          | 片方が「別のスタッフが更新しました」で再確認を求められる                                |
| S4  | 商品の減数・取消（理由つき）                                         | 合計が変わり、「訂正あり」とお客様の履歴に反映される                                    |
| S5  | 売り切れ・販売再開、注文受付の停止・再開                             | お客様の画面に15秒程度で反映される                                                      |
| S6  | 商品名・価格・写真の編集と公開（`canEditMenu`のスタッフ）            | 下書きはお客様に見えず、公開後に反映。価格の変更で古いカートは再確認になる              |
| S7  | スタッフの権限を停止する（管理者が無効化）                           | 次の操作から拒否される                                                                  |
| S8  | 集計で当日の数値を確認する                                           | 注文数・商品数・提供までの時間が、実施した操作と合う                                    |
| S9  | 障害の訓練（Wi-Fiを切る）→ 紙での受付 → 復旧 → 照合                  | [注文障害の手順](incident_runbook.md)のとおりに進められる                               |
| W1  | 各端末のブラウザの開発者ツール（またはリモートデバッグ）             | CSPの`[Report Only]`の違反が出ない（[Hostingのセキュリティヘッダ](hosting_headers.md)） |

## 記録

シナリオごとに、次の項目を記録します。

| 日付 | 版（コミット） | 端末・OS・ブラウザ | 通信 | シナリオID | 結果（合格／不合格） | 課題ID | 担当 |
| ---- | -------------- | ------------------ | ---- | ---------- | -------------------- | ------ | ---- |

### 課題の重大度と再確認

| 重大度 | 例                                                                                       | 扱い                                               |
| ------ | ---------------------------------------------------------------------------------------- | -------------------------------------------------- |
| A      | 注文の欠落・重複、テーブルの取り違え、ほかのお客様の注文の表示、受付済みと誤認させる表示 | 修正して該当のシナリオを確認し直すまで合格にしない |
| B      | 操作はできるが誤解を招く、手順が分かりにくい                                             | 回避策と修正の期限を決める                         |
| C      | 表示の崩れ・文言                                                                         | 期限を決めて修正する                               |

課題を直したら、修正した版で該当のシナリオと、影響しうるシナリオを確認し直して記録します。

## スタッフへの引き継ぎ

| 場面   | 確認すること                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------ |
| 開店時 | ログイン、「メニュー管理」で受付中であることと前日の売り切れの解除、「通知音をオンにする」       |
| 営業中 | 新着の確認、待ち時間の長い注文、状態の更新、訂正（理由を入れる）、お客様が帰ったら「来店を終了」 |
| 閉店時 | 「集計」で当日の数値を確認、ログアウト（共用の端末）                                             |
| 障害時 | [注文障害の手順](incident_runbook.md)のスタッフ向けの手順                                        |

スタッフが手順書を見ながら、通常の操作と障害時の切り替えをできることを、S1〜S9で確かめます。
