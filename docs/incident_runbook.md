# 注文障害の検知と代替受付・復旧の手順

注文の登録・取得・状態の更新ができなくなったときに、スタッフが気づき、営業を続けて復旧できるようにするための手順です。

## スタッフ向けの短い手順

1. **気づく**：スタッフ画面に赤い表示「注文の取得がN分以上止まっています」が出る、またはお客様から「注文できない」「結果がわからない」と言われる。
2. **確かめる（1分）**：端末の通信（Wi-Fi・モバイル回線）を確認し、スタッフ画面の「更新」を押す。別の端末でもスタッフ画面を開く。
3. **切り替える（3分以上直らないとき）**：
   - スタッフ画面が使えるなら、「メニュー管理」で「注文受付を停止する」。お客様の画面に停止の案内が出る。
   - 使えないなら、各テーブルに案内を置き、口頭でも伝える（下の「お客様への案内」）。
   - 紙の注文票で受ける（テーブル番号・品目・数量・受けた時刻・受けたスタッフ）。
4. **連絡する**：システム担当へ、始まった時刻と症状を伝える。デプロイの直後に始まった場合、システム担当は下の「デプロイの切り戻し」を行う。
5. **戻す**：画面に「注文の取得が回復しました」が出たら、下の「復旧と照合」を行ってから、「注文受付を再開する」。

## 検知の対象と判定

| 対象                     | 判定                                                                                       | 知らせ方                                                                                                        | 担当             |
| ------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | ---------------- |
| スタッフ画面の注文の取得 | 最後の成功から失敗が続いて60秒（15秒ごとの取得で4回）を超えた                              | スタッフ画面の上部に赤い表示（どのタブでも表示）。回復したら1回だけ回復の表示                                   | その場のスタッフ |
| 端末の通信               | 端末がオフライン                                                                           | スタッフ画面に「オフラインです」                                                                                | その場のスタッフ |
| お客様の注文の登録       | 送信の結果がわからない、または拒否された                                                   | お客様の画面の案内（[注文API契約](order_api.md)の「送信結果が不明な注文の復旧」）。お客様がスタッフに声をかける | その場のスタッフ |
| スタッフの認証           | ログインできない、権限を確認できない                                                       | スタッフ画面の表示                                                                                              | 店長 → 管理者    |
| 連投の制限               | 制限が発生した                                                                             | スタッフ画面の表示（[新規注文の連投制限](order_limits.md)）                                                     | 店長             |
| Functionsのエラー・遅延  | 例：`createOrder`のエラー率が5分間で5%を超える、`listStaffOrders`が5分間エラーを返し続ける | Cloud Monitoringのアラート（運用開始時に設定する）                                                              | システム担当     |
| 画面のエラー             | 例外                                                                                       | Sentry（`SENTRY_DSN`を設定した場合）                                                                            | システム担当     |

- スタッフ画面の表示は1か所だけに出し、失敗のたびに増やしません。回復の表示も1回だけで、「確認しました」で消えます。短い一時的な失敗（60秒未満）は、停止として知らせません。
- 通知やログに、秘密値・お客様の備考・注文の内容を含めないでください。注文とメニューのFunctionsは、重大度（`severity`）を付けた1行でログを出します。
  - 想定内の拒否（売り切れ・受付停止・価格の変更・連投の制限・店舗やテーブルが見つからないなど）は`WARNING`です。出すのは店舗IDとエラーの種類（`code`・`reason`）だけです。QRの検証で店舗・テーブルが見つからないときは、テーブルIDも出します。連投の制限に達したときは、制限の範囲と回数の行も出します。
  - 想定外のエラー（Firestoreの障害など）は`ERROR`です。店舗ID（QRの検証ではテーブルIDも）と、エラーの内容（スタックを含む）を出します。上の表の「エラー率」のアラートは、この`ERROR`で数えます。
  - 注文の受付は`INFO`で、店舗ID・テーブルID・注文ID・注文番号を出します（`createOrder accepted`）。同じ注文の再送では出しません。
- Sentryへ送る内容は、アプリの側で絞っています。読み取ったQRの文字列・注文の内容・お客様の備考は、エラーの追加情報に入れません。ページのURLに残るテーブルのトークン（`token=`）は、送信の前に`[redacted]`に置き換えます（`src/utils/errorHandler.js`）。

### 運用開始時に決めること

| 項目             | 決める内容                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 現場の責任者     | 店長など。紙での受付への切り替えと再開を判断する人                                                                                      |
| システム担当     | Cloud Monitoring・Sentryの通知を受ける人と連絡先                                                                                        |
| 通知先の所有者   | 通知先のメールやチャットの管理者。担当が変わったら更新する                                                                              |
| 記録を見られる人 | Cloud Logging・Cloud Monitoring・Sentry・店舗の運用の記録を見られる人（案：システム担当と現場の責任者だけ）。担当が変わったら権限を外す |
| 確認の方法       | 運用開始時に、合成の障害（下の「試験」）で、表示と通知が届くことを確かめる                                                              |

## お客様への案内

注文の受付を一時的に止めたときに、テーブルに置く・口頭で伝える文です。

- 日本語：「ただいまスマートフォンからのご注文を一時停止しております。お手数ですが、スタッフにお声がけください。」
- English: "Ordering from your phone is temporarily unavailable. Please ask our staff to take your order."
- 中文：「目前暂停手机点餐。请联系店员点餐。」

## 復旧と照合

二重の調理と受付の漏れを防ぐため、受付を再開する前に照合します。

1. スタッフ画面の「すべて」で、止まっていた時間帯の注文を確認します。
2. 紙の注文票と、テーブル・時刻・品目で照合します。オンラインで受け付け済みの注文を、紙で二重に作らないでください。
3. お客様の画面が「結果を確認できません」だった注文は、受け付けていないと決めつけないでください。お客様の端末の案内（「前回の注文は受け付けられています」など）か、スタッフ画面の一覧で確認してから対応します。
4. 紙で受けた注文は、紙のまま調理・提供まで対応し、オンラインには入力し直しません（二重の調理を防ぐため）。紙の注文は日次の集計に含まれないので、運用の記録に件数を残します。
5. **再開の判定**：スタッフ画面が5分間続けて更新され、スタッフの端末から送ったテストの注文が一覧に届き、状態を更新できることを確かめます。確認できたら「注文受付を再開する」を押し、テストの注文はキャンセルします（理由「動作確認」）。

## デプロイの切り戻し

システム担当の手順です。デプロイの直後に始まった障害は、前に動いていた版へ戻します。戻している間は、上の手順で紙の受付を続けます。戻す先は、デプロイのたびに打つ`deployed-`タグ（[READMEの「公開する場合」](../README.md#公開する場合)）で確かめます。

```bash
git fetch origin --tags
git tag -l 'deployed-*' | sort | tail -3 # 最後が今の版、その前が戻す先
```

1. **Hosting（画面）**：Firebaseコンソールの「Hosting」の「リリース履歴」で、戻す先のリリースにカーソルを合わせ、メニューから「ロールバック」を選びます（[公式の手順](https://firebase.google.com/docs/hosting/manage-hosting-resources#roll-back)）。ビルドし直さずに、そのリリースと同じ内容の配信に戻ります。保持する数の設定を超えた古いリリースは内容が削除されるので、その場合は戻す先のタグを取り出し、`npm ci`のあと、READMEの`npm run build:web`からの手順でデプロイします。開いたままの画面は読み込んだ版のまま動くので、スタッフ画面を再読み込みします。
2. **Functions**：前の版へ戻す操作は公式の文書にないので、戻す先のタグから再デプロイします。

   ```bash
   git switch --detach <戻す先のタグ>
   npm ci --prefix functions
   npx firebase deploy --only functions --project <project-id>
   ```

   - `functions/.env`はGitの管理外なので、タグを取り出しても強制のスイッチの値は変わりません。デプロイ前のチェック（`functions/scripts/check-deploy-env.js`）が表示する3つの値を確かめます。
   - 戻す先の版にない関数があると、CLIが削除するかを尋ねます。「いいえ」（既定）と答えると、残したままデプロイを続けます。`--force`は確認なしで削除するので付けません。

3. **Firestoreのルール**：`git diff --stat <戻す先のタグ> <今のタグ> -- firestore.rules`で差があるときだけ、戻す先のタグを取り出した状態で`npx firebase deploy --only firestore:rules --project <project-id>`を実行します。反映には、新しいクエリとリスナーで最大1分、接続中のリスナーで最大10分かかります（[公式](https://firebase.google.com/docs/firestore/security/get-started#deploying_rules)）。同じページに、Google Cloudコンソールの履歴から以前のルールセットを復元する方法もありますが、次にCLIでデプロイするとファイルの内容で上書きされます。
4. **インデックス**：戻しません。戻す先の`firestore.indexes.json`をデプロイしても、足りないインデックスを作るだけで、ファイルにないインデックスは確認に「はい」と答えない限り削除されません。
5. **記録する**：`git switch -`で元のブランチへ戻ります。Hosting・Functions・ルールを同じタグにそろえたら、そのコミットに新しい`deployed-`タグを打ちます（最後のタグがデプロイ済みの版、という記録を保つため）。一部だけ戻した場合は、何をどのタグへ戻したかを下の「記録」に残します。画面とFunctionsを別々の版で動かす組み合わせは自動テストで確かめていないので、上の「復旧と照合」の再開の判定（テストの注文）を必ず行います。

### 新しい版が書いたデータ

切り戻しで戻るのはコードだけです。Firestoreのデータは、新しい版が書いたまま残ります。戻す前に、`git diff <戻す先のタグ> <今のタグ> -- functions/src`で、保存する項目と判定の変更を確かめます。戻す先の版がある項目を扱うかは、`git grep -c <項目名> <戻す先のタグ> -- functions/src`で確かめられます。現在のコードで、版によって扱いが変わる項目は次のとおりです。

- **注文受付の停止**（店舗の`ordering_enabled`）：この項目を読まない版は、スタッフが受付を停止していても注文を受け付けます。その版へ戻している間は、テーブルの案内と口頭で止めます。
- **強制のスイッチ**（`ENFORCE_APP_CHECK`・`ENFORCE_ORDER_LIMITS`・`ENFORCE_TABLE_TOKEN`）：そのスイッチを読まない版は、`functions/.env`が`true`でも強制しません。
- **注文番号**（`order_counters`の`last_sequence`）：カウンターを使う版どうしなら、戻しても続きの番号を振ります。カウンターを使わない版は、その日の注文の件数から番号を作り、カウンターを進めません。その版で注文を受けたあとに新しい版へ進め直すときは、受付を止めて、その営業日の`last_sequence`を発行済みの最大番号に合わせてから再開します（[注文API契約](order_api.md)の「営業日と注文番号」）。
- **注文の文書**：新しい版が足した項目（`visit_id`・`business_day`・`revision`・`corrected`・`original_quantity`など）は、文書に残ります。商品の減数・取消は、注文の`items`の数量と合計を書き換えて保存しているので、戻したあとも訂正前の数量には戻りません。

## 記録

障害ごとに、始まった時刻・気づいた方法・影響（止まった時間、紙で受けた件数）・対応・再開の時刻を、店舗の運用の記録（非公開）に残します。お客様の個人情報や注文の備考は書きません。

## 試験（合成）

本番の通知の設定や本番のデータを使わずに、次の方法で確かめられます。

- **画面の表示**：`npm run test`（`StaffScreen.test.js`）が、取得の失敗が60秒を超えると停止の表示が1つだけ出ること、タブを切り替えても見えること、回復で回復の表示に変わることを確かめています。
- **手で試す**：テスト用のFirebaseプロジェクトに接続したスタッフ画面で、端末の通信を切って確かめます。画面はローカルのエミュレーターへ接続しないので、[ローカルデモ投入](demo_setup.md)のエミュレーターを止めても表示は変わりません。注文の取得は読み取りだけで、データは書き換えません。
  1. READMEの「自分のFirebase環境で起動する」と「FunctionsのSecretとスタッフ認証」の準備をして`npm run web`で起動し、`/staff`にスタッフのアカウントでログインして、「注文受付」の一覧が出るのを待ちます。
  2. 端末の通信を切ります（Wi-Fiを切る、機内モードにするなど）。次の取得（15秒以内）で「注文を取得できません。接続を確認して「更新」を押してください。表示中の情報は最新ではありません。」が出ます。
  3. そのまま1〜2分待つと、画面の上部に赤い表示「注文の取得が1分以上止まっています（最終取得 …）。」が出ます。「メニュー管理」「集計」に切り替えても、表示は1つだけ出たままです。
  4. 通信を戻します。次の取得（15秒以内）で赤い表示が消え、「注文の取得が回復しました（止まっていた時間 約N分）。」が出ます。「確認しました」を押すと消えます。
- **登録の失敗**：`npm run test:web`が、注文の応答が失われたあとの案内と、再読み込みのあとの復旧を確かめています。
- **認証の失敗**：`npm run test`（`StaffScreen.test.js`）が、注文の取得が認証・権限のエラーで拒否されると、表示中の注文を隠して再ログインを案内し、次に取得できたときに一覧が戻ることを確かめています。サーバーの側は、`npm run test:rules`が、アカウントの無効化・失効・権限の削除で拒否し、再び有効にすると受け付けることを、Authのエミュレーターで確かめています。
- **通知の内容**：`npm run test`（`errorHandler.test.js`、`api.test.js`）が、Sentryへ送る前にURLのトークンを置き換えること、QRの検証の失敗で読み取った文字列を送らないことを確かめています。
