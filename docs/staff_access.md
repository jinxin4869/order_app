# スタッフの認証・店舗権限

管理APIはFirebase Authenticationのログインと、管理者が付与したCustom Claimsを要求します。注文一覧・詳細・状態更新・一括翻訳・単体翻訳は、各リクエストでAuthの現在のアカウント状態と所属も照合します。

```json
{ "role": "staff", "restaurantId": "restaurant-example" }
```

`restaurantId`は所属店舗のFirestoreドキュメントIDです。英数字・`_`・`-`の1〜128文字を使用します。
クライアントから渡されたロールや所属店舗を権限の根拠にしません。

- `updateOrderStatus`は対象注文の`restaurant_id`と所属店舗を照合します。
- `batchTranslateMenu`は対象メニューの店舗と所属店舗を照合します。
- `translateText`はスタッフであることだけを確認します。未認証で公開すると、第三者がDeepLの利用枠と`translation_cache`を消費できるためです。
- 未ログイン・無効化・削除・失効済みのセッションは`unauthenticated`、権限不足・他店舗操作・トークンと現在の所属の不一致は`permission-denied`を返します。
- Authの状態を取得できない場合や失効時刻を確認できない場合は`unavailable`を返し、注文情報の参照・更新や翻訳を実行しません。外部サービスのエラー詳細は返しません。
- お客様の注文作成はログイン不要ですが、Firestoreへの直接書き込みは禁止します。

Claimsの付与・変更は信頼できる管理者環境のAdmin SDKで行います。スタッフ本人にはClaimsを更新する権限を付与しません。

商品名・価格・説明・画像の編集（[メニュー管理](menu_management.md)の「商品情報の編集」）は、全スタッフではなく、`canEditMenu: true`を加えたスタッフだけができます。

```json
{ "role": "staff", "restaurantId": "restaurant-example", "canEditMenu": true }
```

`setCustomUserClaims`はClaims全体を上書きするため、`role`と`restaurantId`も含めて設定します。サーバーは操作のたびにAuthの現在のClaimsを確認します。画面の編集ボタンはログイン時のIDトークンで表示を切り替えるため、付与・取り消しのあとはスタッフに再ログインしてもらってください。
認証情報や秘密鍵をリポジトリへ保存しないでください。

## 停止・所属変更・再有効化

Callableが検証したIDトークンに加え、サーバーがAdmin SDKの`getUser(uid)`を毎回呼び出します。`disabled`、現在の`customClaims`、`tokensValidAfterTime`とトークンの`auth_time`を確認し、認可結果はキャッシュしません。単なるトークン更新では`auth_time`が新しくならないため、失効したセッションには再ログインが必要です。[Firebaseのセッション管理](https://firebase.google.com/docs/auth/admin/manage-sessions)と[Claimsの更新](https://firebase.google.com/docs/auth/admin/custom-claims)を参照してください。

反映の境界は、管理者の変更がAuthに反映された後の次のサーバー認可確認です。既に取得済みの画面データを消す機能や、認可済みで実行中の処理を取り消す機能ではありません。管理API1回あたりAuthへの追加取得が1回あり、Authが利用できない間は管理操作を拒否します。

以下は信頼できる管理者環境でのみ行う手順です。アプリから呼べる管理用APIや秘密鍵の保存先を追加するものではありません。

### 利用停止

1. `await getAuth().updateUser(uid, { disabled: true })`で無効化し、完了を確認します。現在のトークンを持つスタッフも次の認可確認から拒否されます。
2. `await getAuth().revokeRefreshTokens(uid)`で既存のセッションを失効させます。無効化だけで済ませると、再有効化後に古いセッションが復活するため省略しません。
3. 合成環境では停止前のトークンを使い、注文一覧・詳細・状態更新・一括翻訳がすべて拒否され、データが変わらないことを確認します。

### 所属変更・権限の取り消し

1. 変更中の操作を止めるため、一度アカウントを無効化します。
2. 既存セッションを失効させ、管理者が`setCustomUserClaims`で新しい所属・ロールを設定します。このAPIはClaims全体を上書きするため、必要な他のClaimsは管理者が保全します。
3. 所属変更の場合は正しい設定を確認してから再有効化し、スタッフに再ログインを依頼します。権限を取り消す場合はスタッフ権限を除き、必要に応じて無効化を継続します。
4. 途中の操作が失敗した場合は無効化を維持し、設定を確認してから再開します。

現在のClaimsとの照合は失効とは独立して行います。所属変更やロール削除だけをした場合も、旧Claimsのトークンでは操作できません。新しい所属のトークンでも旧店舗の注文は参照・更新できません。

### 再有効化・初回ログイン

1. 無効化を維持したまま既存セッションを失効させ、必要なスタッフ権限と所属を確認します。
2. アカウントを再有効化します。スタッフはログアウトして、失効時刻より後にメールアドレス・パスワードでログインし直します。
3. サインイン時刻と失効時刻は秒単位です。同じ秒にログインと失効が起きる場合も古いトークンを拒否するため、境界の秒を含めて拒否します。初回作成・失効と同じ秒のログインが拒否された場合も、次の秒以降に再ログインしてください。

有効なログインができること、古いトークンが引き続き拒否されること、所属店舗だけを操作できることを確認します。アカウントの停止解除だけで古いセッションを再利用しないでください。

### 機密値なしの検証

`npm run check`で現在の所属照合、失効秒の境界、取得失敗時の拒否、再有効化を単体検証します。`npm run test:rules`はローカルFirestore・Authエミュレーターだけに接続し、合成アカウントが実際にログインして発行されたトークンで、停止・失効・所属変更・権限削除・再有効化・削除を検証します。実アカウントやDeepLには接続しません。

## 操作履歴

状態の変更が成功するたびに、`orders/{orderId}/status_history`へ1件記録します。注文の更新と同じトランザクションで保存するため、競合（`aborted`）・許可されない遷移・他店舗・保存の失敗では記録が残りません。

| 項目                        | 内容                                                                      |
| --------------------------- | ------------------------------------------------------------------------- |
| `from_status` / `to_status` | 変更前（サーバーが読んだ現在の状態）と変更後の状態                        |
| `staff_uid` / `staff_email` | 検証済みのIDトークンのuidとメールアドレス。クライアントの申告は使いません |
| `reason`                    | 任意の理由。100文字まで。HTMLタグと前後の空白を除去します                 |
| `created_at`                | サーバーの時刻                                                            |
| `restaurant_id`             | 注文の店舗                                                                |

- 応答が失われたあとに同じ操作をやり直すと、画面で確認した状態（`expectedStatus`）と一致しないため`aborted`になり、履歴は重複しません。画面は詳細を取り直して、現在の状態を表示します。
- スタッフ画面では、キャンセルするときにだけ理由を入力できます（任意）。理由はスタッフ画面の詳細だけに表示し、お客様には表示しません。
- 閲覧できるのは所属店舗のスタッフだけです。`getStaffOrder`が詳細と一緒に古い順で最大100件を返します。uidは返しません。クライアントからの直接の読み書きはルールで拒否します。
- 履歴は注文と同じ期間保存します。現在、自動での削除はしていません。注文を削除する場合は、Firestoreはサブコレクションを自動で削除しないため、履歴も明示的に削除してください。
- 記録を始める前の状態変更は残っていません（注文の`updated_by`に最後の更新者だけが残ります）。

## 商品の訂正（減数・取消）

注文の詳細の「数量を訂正する（減数・取消）」（`correctOrderItems`）で、受付済みの注文の商品を減らす・取り消すことができます。

| 項目                 | 内容                                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 訂正できる状態       | 未受付・受付済み・調理中。提供待ち・提供済み・対応完了・キャンセルは訂正できません（`failed-precondition`、`reason: "not_correctable"`） |
| できる操作           | 数量を減らす・0にする（取消）だけ。増やす・別の商品に変える場合は、お客様の追加注文で受けます                                            |
| 理由                 | 必須。100文字まで。HTMLタグと前後の空白を除去します                                                                                      |
| 金額                 | 小計・税・合計を、注文時と同じ規則（税抜単価、税10%、円未満切り捨て）でサーバーが計算し直します。画面の金額は目安です                    |
| すべて取り消した場合 | 注文はキャンセルになり、操作履歴にも「全商品の取消：理由」として残ります                                                                 |

- 注文には訂正後の数量と金額を保存し、行ごとの元の数量（`original_quantity`）、最初の合計（`original_total_amount`）、`corrected: true`、版番号（`revision`）を残します。取り消した行も数量0のまま残ります。
- 訂正ごとに`orders/{orderId}/corrections/{operationId}`へ、行・変更前後の数量・変更前後の合計・理由・スタッフ・サーバーの時刻を、注文の更新と同じトランザクションで記録します。クライアントからは読み書きできません。
- 画面で見ていた版番号（`expectedRevision`）が古い場合は`aborted`になり、詳細を取り直します。同じ操作IDの再送は、保存済みの結果を返します。応答が失われた場合も成功とは決めつけず、詳細を取り直して表示します。
- スタッフの一覧には「訂正あり」、詳細には「訂正：3 → 1」「取消」と訂正履歴を表示し、調理・配膳の担当にも訂正が伝わるようにします。
- お客様の注文履歴にも、訂正後の数量・合計と「スタッフが注文内容を訂正しました。」を表示します。
- 会計・返金・POSへの反映は対象外です。

## 来店の終了

注文の詳細の「このテーブルの来店を終了する」（`closeTableVisit`）は、確認のあとでテーブルを空席（`status: "available"`）に戻し、終了時刻（`visit_closed_at`）を記録します。所属店舗のテーブルだけが対象です。
終了すると、お客様の端末からはそれまでの注文履歴が見えなくなり、次のお客様は新しい履歴から始まります。注文そのものや状態は変わりません。お客様が席を立ったあと、片付けのときに押してください。仕様は[注文API契約](order_api.md)の「来店単位の注文履歴」を参照してください。

## 集計

「集計」の切り替えで、所属店舗の1営業日分の注文数・商品数量・人気の商品・提供までの時間を確認できます。定義は[日次の集計](daily_stats.md)を参照してください。

## メニュー管理

「メニュー管理」の切り替えで、商品の売り切れ・販売再開と、店舗の注文受付の停止・再開ができます。仕様と運用は[メニュー管理](menu_management.md)を参照してください。メニュー管理を開いている間も、注文の取得と新着の通知は続きます。

## スタッフ画面

`/staff`を開き、管理者が発行したメールアドレスとパスワードでログインします。Firebase Authenticationのメール／パスワードプロバイダーを有効にし、アカウント作成後に上記Claimsを付与してください。新規登録・パスワード発行はお客様用画面には設けません。ブラウザではタブのセッション内だけログイン状態を保持します。共用端末は利用終了時にログアウトしてください。

`listStaffOrders`と`getStaffOrder`はClaimsの店舗を根拠に取得します。クライアントのFirestore直接readは引き続き拒否します。対応中の注文は未受付・受付済み・調理中・提供待ち・提供済みです。「すべて」で完了・キャンセルも確認できます。最新50件を15秒ごとに取得し、前回の取得後に増えた注文を「新着 N件を確認」で知らせます。押すと一覧（新しい順）の先頭を表示してから件数を消します。スマホで詳細を開いている場合は一覧に戻り、PCでは詳細を開いたまま一覧を先頭までスクロールします。新着の行には「新着」の印が付き、その注文を開くまで残ります。表示の切り替え（対応中／すべて）では新着の件数と印をリセットします。古い注文は「さらに前の注文を読み込む」で確認します。定期更新・手動更新は最新50件へ戻ります。

### 並び順・絞り込み・待ち時間

- 「新しい順」と「待ち時間順」（古い順）を切り替えられます。最新50件より古い未対応の注文は「待ち時間順」で先頭に出ます。どちらも「さらに前の注文を読み込む」で続きを取得します。
- 「未受付 N件（店舗全体）」は、読み込んだ範囲や絞り込みに関係なく、店舗のすべての未受付の注文をサーバーが数えた件数です（Firestoreの`count()`集計）。
- 状態（未受付〜提供済み）とテーブル番号で、読み込み済みの行を絞り込めます。絞り込み中は「読み込み済みのN件のうちM件を表示」と表示します。新着と未受付の件数は絞り込みで変わりません。
- 対応中の注文には「経過 N分」を表示します（30秒ごとに更新）。未受付のまま10分を過ぎた注文は「待ち時間が長い注文」と強調します。

### 新着の通知

- 新着の判定は、前回の取得後に増えた注文IDです。最初の取得、「さらに前の注文を読み込む」、同じ注文の再取得では通知しません。表示の切り替え（対応中／すべて、新しい順／待ち時間順）とログアウトで、新着の記録をリセットします。
- 「待ち時間順」では、読み込んだ範囲に入った新しい注文だけを新着として数えます。店舗全体の未受付の件数は、常に上の件数で確認してください。
- 通知音は、ブラウザが利用者の操作なしに音を出せないため、既定ではオフです。「通知音をオンにする」を押すと有効になり、確認の音が1回鳴ります。ページを開き直したら、もう一度押してください。対応している端末（Androidのブラウザなど）では振動もします。ネイティブ版では音と振動を使いません。
- 音が出せない端末では、その旨を表示します。音が出ない場合も、「新着 N件を確認」のボタン、行の「新着」の印、ブラウザのタブのタイトルの「(N)」で知らせます。

### 通信の切断と復帰

- 注文の取得が60秒を超えて失敗し続けると、どのタブでも上部に赤い表示「注文の取得がN分以上止まっています」を出します。回復すると「注文の取得が回復しました（止まっていた時間 約N分）」を1回だけ表示します。対応は[注文障害の検知と代替受付・復旧](incident_runbook.md)を参照してください。

- 端末がオフラインのときは「オフラインです。注文を取得できません。表示中の情報は最新ではありません。」と表示します。最終取得時刻も表示します。
- オンラインに戻ったとき、スリープや別のタブから画面に戻ったとき（`AppState`が`active`になったとき）は、15秒を待たずにすぐ取得します。

注文を選択すると料理・数量・要望と合計を確認できます。変更ボタンは許可された次の状態だけを表示し、確認後に実行します。`updateOrderStatus`は`expectedStatus`（画面で確認した状態）を必須とし、トランザクション内で比較します。競合は`aborted / status_changed`を返し、画面は詳細を再取得して再確認を求めます。自動で次の状態へ進めません。通信応答が失われた場合も再取得してから判断します。

「対応完了」は注文の作業終了を表し、決済済みという意味ではありません。POS・会計連携とテーブルの会計後の解放はこの画面の対象外です。

スタッフ画面を公開する前に、新しいFunctionsとFirestoreインデックスを反映してください。既存クライアントが`updateOrderStatus`を直接使っている場合は、`expectedStatus`を送る形へ同時に更新する必要があります。
