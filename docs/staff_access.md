# スタッフの認証・店舗権限

管理APIはFirebase Authenticationのログインと、管理者が付与したCustom Claimsを要求します。注文一覧・詳細・状態更新・一括翻訳・単体翻訳は、各リクエストでAuthの現在のアカウント状態と所属も照合します。

```json
{ "role": "staff", "restaurantId": "restaurant-example" }
```

`restaurantId`は所属店舗のFirestoreドキュメントIDです。英数字・`_`・`-`の1〜128文字を使用します。
クライアントから渡されたロールや所属店舗を権限の根拠にしません。

- `updateOrderStatus`は対象注文の`restaurant_id`と所属店舗を照合します。
- `batchTranslateMenu`は対象メニューの店舗と所属店舗を照合します。
- `translateText`はスタッフであることだけを確認します。未認証で公開すると、第三者がDeepLの利用枠と`translation_cache`を消費できるためです。
- 未ログイン・無効化・削除・失効済みのセッションは`unauthenticated`、権限不足・他店舗操作・トークンと現在の所属の不一致は`permission-denied`を返します。
- Authの状態を取得できない場合や失効時刻を確認できない場合は`unavailable`を返し、注文情報の参照・更新や翻訳を実行しません。外部サービスのエラー詳細は返しません。
- お客様の注文作成はログイン不要ですが、Firestoreへの直接書き込みは禁止します。

Claimsの付与・変更は信頼できる管理者環境のAdmin SDKで行います。スタッフ本人にはClaimsを更新する権限を付与しません。
認証情報や秘密鍵をリポジトリへ保存しないでください。

## 停止・所属変更・再有効化

Callableが検証したIDトークンに加え、サーバーがAdmin SDKの`getUser(uid)`を毎回呼び出します。`disabled`、現在の`customClaims`、`tokensValidAfterTime`とトークンの`auth_time`を確認し、認可結果はキャッシュしません。単なるトークン更新では`auth_time`が新しくならないため、失効したセッションには再ログインが必要です。[Firebaseのセッション管理](https://firebase.google.com/docs/auth/admin/manage-sessions)と[Claimsの更新](https://firebase.google.com/docs/auth/admin/custom-claims)を参照してください。

反映の境界は、管理者の変更がAuthに反映された後の次のサーバー認可確認です。既に取得済みの画面データを消す機能や、認可済みで実行中の処理を取り消す機能ではありません。管理API1回あたりAuthへの追加取得が1回あり、Authが利用できない間は管理操作を拒否します。

以下は信頼できる管理者環境でのみ行う手順です。アプリから呼べる管理用APIや秘密鍵の保存先を追加するものではありません。

### 利用停止

1. `await getAuth().updateUser(uid, { disabled: true })`で無効化し、完了を確認します。現在のトークンを持つスタッフも次の認可確認から拒否されます。
2. `await getAuth().revokeRefreshTokens(uid)`で既存のセッションを失効させます。無効化だけで済ませると、再有効化後に古いセッションが復活するため省略しません。
3. 合成環境では停止前のトークンを使い、注文一覧・詳細・状態更新・一括翻訳がすべて拒否され、データが変わらないことを確認します。

### 所属変更・権限の取り消し

1. 変更中の操作を止めるため、一度アカウントを無効化します。
2. 既存セッションを失効させ、管理者が`setCustomUserClaims`で新しい所属・ロールを設定します。このAPIはClaims全体を上書きするため、必要な他のClaimsは管理者が保全します。
3. 所属変更の場合は正しい設定を確認してから再有効化し、スタッフに再ログインを依頼します。権限を取り消す場合はスタッフ権限を除き、必要に応じて無効化を継続します。
4. 途中の操作が失敗した場合は無効化を維持し、設定を確認してから再開します。

現在のClaimsとの照合は失効とは独立して行います。所属変更やロール削除だけをした場合も、旧Claimsのトークンでは操作できません。新しい所属のトークンでも旧店舗の注文は参照・更新できません。

### 再有効化・初回ログイン

1. 無効化を維持したまま既存セッションを失効させ、必要なスタッフ権限と所属を確認します。
2. アカウントを再有効化します。スタッフはログアウトして、失効時刻より後にメールアドレス・パスワードでログインし直します。
3. サインイン時刻と失効時刻は秒単位です。同じ秒にログインと失効が起きる場合も古いトークンを拒否するため、境界の秒を含めて拒否します。初回作成・失効と同じ秒のログインが拒否された場合も、次の秒以降に再ログインしてください。

有効なログインができること、古いトークンが引き続き拒否されること、所属店舗だけを操作できることを確認します。アカウントの停止解除だけで古いセッションを再利用しないでください。

### 機密値なしの検証

`npm run check`で現在の所属照合、失効秒の境界、取得失敗時の拒否、再有効化を単体検証します。`npm run test:rules`はローカルFirestore・Authエミュレーターだけに接続し、合成アカウントが実際にログインして発行されたトークンで、停止・失効・所属変更・権限削除・再有効化・削除を検証します。実アカウントやDeepLには接続しません。

## スタッフ画面

`/staff`を開き、管理者が発行したメールアドレスとパスワードでログインします。Firebase Authenticationのメール／パスワードプロバイダーを有効にし、アカウント作成後に上記Claimsを付与してください。新規登録・パスワード発行はお客様用画面には設けません。ブラウザではタブのセッション内だけログイン状態を保持します。共用端末は利用終了時にログアウトしてください。

`listStaffOrders`と`getStaffOrder`はClaimsの店舗を根拠に取得します。クライアントのFirestore直接readは引き続き拒否します。対応中の注文は未受付・受付済み・調理中・提供待ち・提供済みです。「すべて」で完了・キャンセルも確認できます。最新50件を15秒ごとに取得し、前回の取得後に増えた注文を「新着 N件を確認」で知らせます。押すと一覧（新しい順）の先頭を表示してから件数を消します。スマホで詳細を開いている場合は一覧に戻り、PCでは詳細を開いたまま一覧を先頭までスクロールします。新着の行には「新着」の印が付き、その注文を開くまで残ります。表示の切り替え（対応中／すべて）では新着の件数と印をリセットします。古い注文は「さらに前の注文を読み込む」で確認します。定期更新・手動更新は最新50件へ戻ります。端末のスリープやオフライン中は取得されないため、再開時に「更新」を押してください。

注文を選択すると料理・数量・要望と合計を確認できます。変更ボタンは許可された次の状態だけを表示し、確認後に実行します。`updateOrderStatus`は`expectedStatus`（画面で確認した状態）を必須とし、トランザクション内で比較します。競合は`aborted / status_changed`を返し、画面は詳細を再取得して再確認を求めます。自動で次の状態へ進めません。通信応答が失われた場合も再取得してから判断します。

「対応完了」は注文の作業終了を表し、決済済みという意味ではありません。POS・会計連携とテーブルの会計後の解放はこの画面の対象外です。

スタッフ画面を公開する前に、新しいFunctionsとFirestoreインデックスを反映してください。既存クライアントが`updateOrderStatus`を直接使っている場合は、`expectedStatus`を送る形へ同時に更新する必要があります。
